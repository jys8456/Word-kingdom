## 1. 진행 방식 (승인 게이트)

```
문서 작성 → [G0 문서 승인] → 디자인 → [G1 디자인 승인] → 개발(PR 단위) → [G3 빌드 승인]
         → 확장 → [G4] → 사용자 테스트 → [G5 출시 결정] → 스토어 출시
```

- 모든 작업은 **GitHub 이슈 → 브랜치 → PR → 리뷰 → 머지** 순서로 진행합니다.
- PR에는 변경 요약, 관련 PRD 요구사항 ID(F-xx), 스크린샷(모바일 360폭), 테스트 결과를 붙입니다.
- **오너 승인(✅) 없이 다음 단계로 넘어가지 않습니다.** 범위 밖 작업은 별도 이슈로 제안만 합니다.

## 2. 기술 스택

### 2.1 후보 비교

| 기준 | **A. React + Vite + Capacitor** (추천) | B. Flutter | C. React Native (Expo) |
|---|---|---|---|
| 웹 테스트 링크 배포 (P5) | ◎ 그대로 웹 | △ Flutter Web (무겁고 느림) | ○ Expo Web (제약 있음) |
| Android/iOS 출시 | ○ 웹을 네이티브 셸로 감쌈 | ◎ 네이티브 렌더링 | ◎ 네이티브 컴포넌트 |
| 퍼즐 UI (격자·드래그·애니메이션) | ◎ CSS/DOM으로 빠르게 | ◎ | ○ |
| 2주 MVP 속도 | ◎ | ○ | ○ |
| iOS 심사 4.2 (웹 래핑 거절) 리스크 | △ 앱다운 기능으로 보완 필요 | 없음 | 없음 |
| 이후 유지보수 (1인 개발) | ◎ 한 코드베이스 | ○ Dart 학습 | ○ |

### 2.2 결정 (승인 요청 D1)
**A안: React + TypeScript + Vite, 앱은 Capacitor로 감싸기. 서버·관리자는 Supabase.**

이유: MVP의 목적은 **웹 링크로 빠르게 가설 검증**(PRD §2)이고, 검증이 되면 **같은 코드**로 스토어에 올릴 수 있습니다. 관리자 웹도 같은 언어·같은 퍼즐 엔진을 쓰므로 1인 개발로 유지보수가 가능합니다. iOS 4.2 리스크는 오프라인 동작·햅틱·로컬 알림·네이티브 TTS로 보완합니다.

### 2.3 전체 구성
```
                  ┌───────────────────── 모노레포 (GitHub 저장소 1개) ─────────────────────┐
                  │  apps/game      게임 (웹 · Android · iOS)                              │
                  │  apps/admin     관리자 웹                                               │
                  │  packages/engine   퍼즐 엔진 · 검사 규칙 · 별 계산 (순수 TS)  ← 둘이 공유 │
                  │  packages/ui       디자인 시스템 컴포넌트                     ← 둘이 공유 │
                  │  packages/content  콘텐츠 형식 정의(스키마) · 검사            ← 둘이 공유 │
                  │  supabase/      DB 구조 · 권한 규칙 · 서버 함수 (Git으로 관리)           │
                  └──────────────────────────────────────────────────────────────────────┘
게임 앱 ⇄ Supabase (콘텐츠 내려받기 · 로그 올리기 · 원격 설정)   관리자 웹 ⇄ Supabase (로그인 필수)
```

## 3. 저장소 구조와 브랜치 전략

### 3.1 기존 시안 코드 정리 (G0 승인 후 첫 작업)
1. 현재 커밋에 `prototype-v0` 태그 → 참고용 보존
2. 시안 화면 코드 제거, 재사용 대상(콘텐츠 JSON·검증 로직·테스트)만 새 구조로 이동

### 3.2 폴더 구조 (모노레포)
```
word-kingdom/
├─ docs/                       PRD · UX · 관리자 · 개발 계획 · 운영 · ADR · runbook
├─ apps/
│  ├─ game/                    게임 앱
│  │  ├─ src/app/              라우팅, 앱 진입
│  │  ├─ src/features/         map · crossword · wordsearch · review · collection · recap · settings
│  │  ├─ src/platform/         저장·발음·진동·알림 어댑터 (웹/앱 분기는 여기서만)
│  │  ├─ src/sync/             콘텐츠 내려받기 · 원격 설정 · 로그 전송 (오프라인 큐)
│  │  ├─ android/ ios/         Capacitor 생성 (P6)
│  │  └─ e2e/                  Playwright
│  └─ admin/                   관리자 웹
│     └─ src/features/         dashboard · words · themes · puzzle-editor · audio · publish
│                              · notices · remote-config · support · experiments · accounts · audit
├─ packages/
│  ├─ engine/                  퍼즐 엔진 (순수 TS, React 없음) + 테스트
│  ├─ content/                 콘텐츠 스키마(Zod) · 검사 규칙 · 기본 내장 콘텐츠
│  └─ ui/                      디자인 토큰 · 공통 컴포넌트 (게임·관리자 미리보기 공유)
├─ supabase/
│  ├─ migrations/              DB 구조 변경 (Git으로 리뷰)
│  ├─ functions/               서버 함수 (발행, 집계)
│  └─ seed.sql                 로컬 개발용 데이터
├─ scripts/                    퍼즐 배치 보조, 음성 생성, 콘텐츠 백업
└─ .github/workflows/          CI
```
원칙: **게임 로직(엔진)은 React와 분리된 순수 TypeScript.** 게임과 관리자 미리보기가 같은 엔진을 쓰므로 "관리자에선 됐는데 게임에선 깨지는" 문제가 생기지 않음.

### 3.3 브랜치
- `main`: 항상 배포 가능. 직접 푸시 금지, PR로만.
- `feat/F-02-crossword`, `fix/…`, `docs/…`: 기능 단위 브랜치 → PR → 리뷰 → 스쿼시 머지
- 커밋 메시지: `feat(crossword): 힌트 3단계 추가 (F-02 AC7)` 형식

### 4.4 발음(TTS) 전략 — 플랫폼별
| 단계 | 방식 | 이유 |
|---|---|---|
| 웹 (P3~P5) | 브라우저 `speechSynthesis` | 무료, 즉시 |

## 6. 앱 스토어 출시 계획

### 6.1 순서
1. **Android (Google Play)** — 국내 Android 점유율이 높고, 심사가 비교적 빠름
2. **iOS (App Store)** — Mac + Xcode 필요, 심사 기준 더 엄격

### 6.2 사전 준비 (지금부터 고려해서 개발)
| 항목 | 내용 | 반영 시점 |
|---|---|---|
| 앱 ID | `com.<회사/개인>.wordkingdom` 확정 (나중에 못 바꿈) | P2 |
| 화면 방향 | 세로 고정 | P2 |
| 안전 영역 | 노치·홈 인디케이터 여백 (`env(safe-area-inset-*)`) | P2 |
| 오프라인 | 콘텐츠·폰트·음성 앱 내장 | P2~P4 |
| 뒤로가기 | Android 하드웨어 뒤로가기 = 화면 ✕와 동일 동작 | P3 |
| 데이터 저장 | 앱 삭제 전까지 유지 (Capacitor Preferences) | P2 |
